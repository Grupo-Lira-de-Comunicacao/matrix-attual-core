# M4 revocation receipts — candidate, not accepted for production

Existing explicit M4 session: the same bearer presented to the unlink route returns the same bounded receipt, without reauthorizing that session. The Matrix records withdrawals, revokes sessions/links/pending bridge codes, suppresses pending delivery, and stores the operation in one transaction. Subsequent requests use the same One callback correlation; Matrix only confirms after a matching One receipt and successful persisted confirmation. Existing AttualPlay draft retry behavior is compatible. Never send the receipt's bearer or logs to third parties.

This branch depends on One draft #44 for atomic suppression and idempotent acknowledgment. Migration 027 does not use institutional migration 026; **never push all migrations to production** to deploy this candidate. Test the exact candidate artifacts and confirm database backup/rollback, version pairing, and effective privileges in isolated staging before promotion.

Open gates: test full schema and two-connection behavior, including lock ordering, in-flight consent writes and reauthorization by a fresh verified link; wire and validate a periodic, authenticated runner for the candidate reconciliation endpoint; agree retention/cleanup, recovery for expired or legacy credentials, and rights handling with the responsible privacy owner. The seven-day receipt lookup window is provisional; it does not delete the record or unblock a pending operation. Out-of-order One callbacks across a new link generation need explicit fencing before acceptance. Selective personalization withdrawal uses the pre-existing endpoint and is not covered by these full-unlink changes. Verify the E2E run, including fail-closed behavior between Matrix commit and One suppression acknowledgment. This candidate is not sufficient to close Issue #10.

Local evidence: run the normal service tests and, on a non-production checkout with the optional PGlite package, `node tests/sql/m4_revocation_receipts_pglite.mjs`. SQL tests use an in-memory fixture schema. They are not a substitute for tests against the real isolated integration environment.

The candidate provides `POST /v1/internal/m4/reconcile-revocations` for an authenticated internal runner; no scheduled job is enabled by this branch. It claims at most four pending receipts, honors a bounded lease and retries with backoff, uses the original operation ID, confirms only after One success, and returns aggregate counts. Do not point the runner at production before approval of rollout gates.
